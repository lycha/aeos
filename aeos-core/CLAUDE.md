# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

AEOS is a CLI that drives tickets through LLM-agent pipelines. A ticket is an **epic** or a **task**, and each has its own column sequence:

- **epic** — `BACKLOG → SPEC_REVIEW → TECH_SPEC → TASK_BREAKDOWN → INTEGRATION_REVIEW → DOD_GATE → DONE`
- **task** — `BACKLOG → IMPLEMENTATION → CODE_REVIEW → QA → DONE`

Those are identifiers. What each column does is declared by its spec (see Column roles), not implied by its name.

`SPEC_REVIEW` reviews a spec a person wrote (`spec-reviewer-agent` → `spec-review.md`: gaps, ambiguities, contradictions, untestable criteria); it never drafts requirements, and approving out of it is the spec gate. `ticket create` refuses an epic without `--spec`. Each column has a worker agent, a reviewer agent with rubrics, and a human approval gate. An epic decomposes into child tasks and cannot leave `TASK_BREAKDOWN` until every child is `DONE`. `aeos orchestrator run <epicId>` drives the whole thing autonomously. See `README.md` for the full command surface, state machine table, and executor matrix — that document is current; prefer it over re-deriving behaviour from code.

AEOS dogfoods itself: `.aeos/` in this repo is a live project directory (key `AEOS`), not fixtures.

CI (`.github/workflows`) runs typecheck → lint → build → test on Node 22. Match that order locally before pushing.

## Architecture

Hexagonal, with a strictly enforced dependency direction:

```
cli/ → application/ → domain/ ← infrastructure/
```

- **`src/domain/`** — pure. Zero external imports, no I/O. Contains `model/` (Ticket, Column, SubState, specs, events), `services/` (`state-machine.ts`, `output-validation.ts`), and `ports/` split into `driving/` (use-case interfaces the CLI calls) and `driven/` (interfaces infrastructure implements).
- **`src/application/`** — use cases, one per CLI verb (`ticket-run.use-case.ts`, `ticket-approve.use-case.ts`, …), plus `services/` for context assembly, prompt building, preflight, decision promotion, and executor-config resolution.
- **`src/infrastructure/`** — adapters: `persistence/` (better-sqlite3), `filesystem/`, `git/` (simple-git), `executor/`, `spec-loader/` (YAML + Zod).
- **`src/cli/`** — one handler per command in `commands/`, the Commander registration generated from the contract in `generated/`, the resource guards in `resources.ts`, the Ink/React TUI in `ui/`, and the composition root `container.ts`.

When adding a capability, the shape is: driving port → use case → driven port(s) → adapter(s) → wire in `container.ts` → a handler for the command the contract describes (see Generated command registration). Adding an import of Node built-ins or npm packages into `domain/` is a layering violation.

### Composition root

`src/cli/container.ts` builds everything eagerly _except_ SQLite repositories, which are lazy singletons. This is deliberate: `aeos install` and `aeos project init` must run before `~/.aeos/state.db` exists, so touching `getDb()` at container-construction time would break first-run. Keep new DB-backed dependencies lazy.

### TicketRunUseCase

`src/application/ticket-run.use-case.ts` is the core. One `execute()` call runs the column cycle: eligibility → context → preflight → `WORKING` → **revision loop** → `IN_REVIEW` → `SIGNED_OFF`. The loop body (`runAttempt`) is worker (`invokeWorker`) → validate → checks → commit artifact → reviewer → parse verdict; `decideNextAttempt` then says advance, retry, or escalate. It emits `ticket-run.*` events through a `TicketRunObserver`, which is what the Ink TUI renders live. Executors are injected as a `createExecutor(agentSpec)` factory, because worker and reviewer resolve to different executors within one run.

Two invariants that were previously violated and are easy to re-break:

1. **The reviewer verdict comes from a parsed trailer, never the prose.** `domain/services/verdict-parser.ts` reads an `AEOS-VERDICT` HTML comment. Substring-matching the review text misfires on the reviewer's own output-format template. A missing or unparseable trailer escalates — it is never coerced into a pass or a rejection.
2. **Escalation is not failure.** `SubState.ESCALATED` means the pipeline worked and needs a human (preflight blockers, iteration cap, non-convergence, unparseable verdict). `FAILED` means something broke. The orchestrator and `aeos ticket show` rely on the distinction.

### Checks stage

On a column whose spec has `runChecks: true`, the `checks` list of `.aeos/project.json` runs after validation and before the artifact commit (`runChecks` in `TicketRunUseCase`). A check is the `Check` interface in `domain/model/check.ts`, not a command: `CheckRegistry` (`application/checks/`) builds one `ShellCheck` per configured entry and appends anything passed to `register()`, and **the stage must never assume a check is a process** — command strings and exit codes live in `ShellCheck` and the `ChecksRunner` adapter (`infrastructure/checks/`) only. That is the seam for in-process checks. A failure returns the `checks-failed` outcome: the reviewer is not invoked, `decideNextAttempt` treats it as a rejection with blocker topic `check:<name>` (and never as `mark_done`), and the next worker gets the output as `previous-checks.md`. A pass writes `<ticket>-checks.md` into the ticket directory, which is how it reaches the reviewer's re-assembled context. Each stage writes a run record (`role: checks`, `executor: shell`, no brief).

### Criterion tracing (pre-worker check)

`Check.phase` is `'post-worker' | 'pre-worker'`. `CheckRegistry.preWorkerChecksFor(ticket, specPin, role)` returns the built-in `CriteriaTraceCheck` (`application/checks/`, in-process, spawns nothing) for a spec-backed epic in a column whose role is `integration`, whatever `project.json` lists. `TicketRunUseCase` runs it in `runPreWorkerChecks`, **before preflight**, so a failure invokes no executor; it returns an `Escalation` (`PRE_WORKER_CHECK_FAILED`, `attempts: 0`) and the ticket ends `ESCALATED`, never back to the worker. `performChecks` is shared with the post-worker stage and writes the run record (`executor: in-process`); files a check names in `CheckResult.artifacts` are committed with it. The logic is the pure `domain/services/criteria-trace.ts` (`parseCriteria` reads bold `**AC-n**` definitions, `parseFeature`, `testTags`, `traceCriteria`); `CriteriaCollector` (`application/services/`) feeds it: spec and `.feature` files through git at the pin, test files through `listFiles`/`showFile` at the project's `HEAD` filtered by `criteria.testGlobs` (the path guard's glob rules), claims from `Ticket.implements` (migration v11, `ticket create --implements`, `- Implements:` in the ticket document, `Implements:` commit trailer). The same collector gives the reviewer of the `decomposition` column `criteria-claims.md`, and `ContextAssembler` uses `scenariosFor` to give a task that claims criteria only the scenarios tagged with them (claims are read from the ticket document).

### Conformance report

`domain/model/conformance-report.ts` mirrors the human-owned `conformance.schema.json`; the pure `domain/services/conformance-builder.ts` builds it from a `CriteriaTrace` and `TestResult[]` and serialises it (Markdown table, and YAML through a small emitter of its own, because `domain/` and `application/` import no npm package; the builder test reads the YAML back with `js-yaml` and validates against the schema with `ajv`). Verdict rule, in `verdictOf`: any failed instrument → `fail`; one passed, none failed → `pass`; none → `unverified`; a skipped test is no instrument. `addInstruments` adds agent and human instruments and recomputes by the same rule, so nobody outvotes a failed test. `ConformanceService.buildConformance(projectPath, epicId)` (`application/services/`) runs `criteria.testReport.command` through the `ChecksRunner` port, reads the report through the `TestReportReader` port (`infrastructure/test-report/vitest-json-reader.adapter.ts`; a reader throws on a format it does not read, so `junit` is a new adapter and no caller changes), makes file paths relative to the project root to match the trace, and builds. `meta.code.base` is the commit of the `aeos-base/<epic>` tag (`GitGateway.commitOf`), left out only when there is no such tag. `scaffoldDefaults` writes `.aeos/.gitignore` (`tmp/`) when there is none.

**At the final gate** (the column whose role is `final-gate`) two use cases call it:

- `TicketRunUseCase` (`writeConformance`, before the context is assembled) commits the report as `<id>-conformance.md` in the ticket directory, which is how it reaches the worker's and the reviewer's context, ending with `Judge exactly these criteria: …` when any is unverified. `RunContext.judging` holds those ids: empty means no preflight and no attempt (`noAgent`), straight to `SIGNED_OFF`. Otherwise the column's worker (`conformance-agent`) runs, and after its artifact is committed `parseConformanceVerdicts` (`domain/services/conformance-verdict-parser.ts`, the `AEOS-CONFORMANCE` block, one `AC-n: pass|fail | justification` line each) must find exactly those ids, or the run escalates `UNPARSEABLE_VERDICT` before the reviewer is asked. Like the review verdict, it is never read from prose and never coerced. The gate's spec declares `diffContext: epic`, so its agents are given the epic's `base..HEAD` diff. `ticket run` still refuses the gate for a ticket with no spec. The orchestrator runs the column once for a spec-backed epic (`READY` there), then halts `HUMAN_GATE`; with no spec, or already `SIGNED_OFF`, it halts without running.
- `TicketDodApproveUseCase.review` rebuilds the report at approval time, adds the verdicts of the column's last worker run as `agent` instruments (evidence: the run record's path), **only if the ticket is `SIGNED_OFF` and only for criteria still unverified**, and a `human` instrument per `--verified` id. `execute` takes that `DodReview` back (a spec-backed ticket is refused without it), refuses a yes with no reason while anything is failed or unverified, and records the gate with an `alongside` callback: `GateRecordStore.append` writes the files it returns beside the gates file and commits them **in the same commit as the record**, which is how `conformance.yaml`/`.md` and the decision land together and how the human instrument can cite `features/<feature>/gates.yaml#GATE-n`. After `DONE`, `PullRequestGateway.updateBody` (`gh pr view`/`gh pr edit`) fills the `<!-- aeos:conformance -->` section through `fillConformance`; a failure there is a `warning` on the result, not an error, since the decision is already recorded. `ticket show` excludes the two conformance files from the "spec has moved" check, as it does `gates.yaml`.

### The bug track

`ticket create --bug` makes a standalone `TASK` with `track: 'bug'` (`tickets.track`, migration v12; refused with `--parent`/`--spec`). For such a ticket on a column whose worker is agentic (`RunContext.bugTrack`, set from the worker agent's `bugTrack: { reproduce, fix }`; it keys on `executorMode`, not on the column), `runAttempt` calls `invokeWorker` twice, each with its phase's instruction in place of `taskInstruction` and `ExecutorInvocation.bugPhase` set:

- `reproduce()`: worker → `parseRepro` (`domain/services/repro-parser.ts`, exactly one `AEOS-REPRO` block or `UNPARSEABLE_REPRO` escalation) → `ReproCheck('red')` through `performChecks` (a checks run record) → on exit zero a `checks-failed` outcome named `repro-red` ("does not reproduce the bug"), so the loop retries the phase → otherwise hash every changed file (`FileHasher` port), commit them to the **project** repository as `[<id>][REPRO]`, and persist `<id>-repro.json` (`ReproState`, `application/services/repro-evidence.ts`).
- The fix: `readRepro` finding that file is what makes every later attempt **and every later run** skip phase A. After the worker, changed hashes fail the attempt and the files are restored; then `proveFixed` runs `ReproCheck('green')` (`checks-failed` as `repro-green` on a non-zero exit) and writes `<id>-repro.md`, committed with the artefact. `TicketApproveUseCase` puts it in the pull request body.

`ReproCheck` (`application/checks/`) is a `Check` whose `passed` means "as expected" and which keeps the exit code for the evidence. The reproduce-phase worker run is recorded alone, with no `output`: the fix's notes are the task's artefact. The context assembler leaves `<id>-repro.json` out of prompts. The stub plays both phases by `bugPhase` (a script that exits 1 until its fix file exists), so the end-to-end harness's `createStandaloneTask` is `ticket create --bug` and every standalone task there is a bug.

### Protected paths

`TicketRunUseCase` snapshots `gitGateway.changedFiles` of both repositories (the project and `.aeos/`) immediately before each executor invocation and again immediately after (`changedPaths` / `restoreProtected`); the worker's snapshot is taken after the `[BASELINE]` commit. New entries matching `protectedGlobs` (`domain/services/path-guard.ts`: built-in defaults plus `protectedPaths` from `project.json`, which can only add) are restored with `restoreFiles` and the attempt returns `failed` with the files named, also in the run record's `error`. Keep the window tight around the executor call: the engine writes under `.aeos/tickets/` itself straight afterwards. Because the check is a set difference, a protected file that is already uncommitted before the run is not guarded: `ProjectInitUseCase.commitScaffold` commits the scaffold in `.aeos` for that reason (and throws with the `git config` fix when the commit does not take), which leaves an operator's own uncommitted edit as the gap (the `shortcut` comment on `restoreProtected`). The end-to-end harness's `stubWorkerTouches(<path>)` makes every stub worker run edit that file; shipped code has no such hook.

### Generators and the contract gate

Both are lists in `project.json` (`generators`, `contracts`; `GeneratorConfig` in `domain/model/project-executor-config.ts`, validated in `FsProjectRepository.readExecutorConfig`), resolved once into `RunContext`: generator `outputs` are added to `protectedGlobs`, generator `inputs` to `contractGlobs`.

- **Generators** (`runGenerators`, in `runAttempt` after the `[BASELINE]` commit, agentic columns that require a repository diff (`requiresRepoDiff !== false`; a decomposition run may be on the default branch), **first attempt only**, because `commitFiles` commits whatever is staged and later attempts carry the worker's staged work). Inputs are the tracked and changed files the globs match (`findViolations` is the one glob matcher), hashed through `FileHasher`; the stamp is in `.aeos/tmp/generators.json` behind the `GeneratorStampStore` port. The command runs as a `ShellCheck` from `CheckRegistry.generatorCheck` through `performChecks(…, 'generator')`, which is what writes the run record (`role: generator`, no verdict). A failure returns `failed` before any executor call. Outputs are committed to the project as `[<ticket>][GENERATED] <name>`.
- **Contract mark.** `invokeWorker` matches the paths the worker's run added to `changedPaths` against `contractGlobs` and calls `TicketRepository.setContractChange` (`tickets.contract_change`, migration v14, a `ContractChange` as JSON: `paths` and `approvedBy`), resetting `approvedBy`. A protected path never gets this far: that check restores it and fails the attempt first.
- **The gate** is in `TicketApproveUseCase`, before anything is committed or pushed: an unapproved `contractChange` is refused unless a person passes `contract` (`--contract`); `byEngine` is refused whatever it passes, which is how the orchestrator halts (`NEEDS_HUMAN`, its existing answer to a failed approval; the policy needed no change). With it, a `contract` gate record (the paths are its `reason`) is written just before the column's own record, and `approvedBy` is set, so later columns do not ask again. `ticket show --json` reports it as `ticket.contractChange` (null when there is none). The CLI maps the refusal by wording to `CONTRACT_APPROVAL_REQUIRED`, exit 3.
- **Bugs.** After the fix's artefact is committed, a fix whose run touched a contract path returns an escalation (`EscalationReason.CONTRACT_CHANGE`) and the reviewer is not asked.

### Branches, commits and pull requests

Engine commits never land on the default branch. The orchestrator isolates an epic on `aeos/<epicId>` (`setUpGitIsolation`, before the epic is marked running). `GitGateway.ensureOnBranch` creates a new branch from the default branch's local tip, wherever `HEAD` is, checks an existing one out as it is, and throws when uncommitted changes prevent the switch (a `failed` run, nothing changed); `TicketRunUseCase.isolateTask` does the same for a task before any executor runs: a child task goes onto its epic's `aeos/<epicId>`, a standalone task onto `aeos/<taskId>` (tag `aeos-base/<taskId>`). `TicketApproveUseCase` commits a finished task with `buildTaskCommitMessage` (`application/services/pull-request-text.ts`; `Ticket:`/`Epic:` trailers, extra trailers as an argument), then, **before the column transition**, pushes `aeos/<id>` and opens the pull request through the `PullRequestGateway` port: an epic leaving `INTEGRATION_REVIEW`, a standalone task reaching `DONE`. The order matters: a failure returns an error with the ticket still `SIGNED_OFF`, so re-running approve retries; the orchestrator halts `NEEDS_HUMAN` on any failed approval instead of looping on it. The URL is stored in `tickets.pr_url` (migration v8). `GhPullRequestGateway` (`infrastructure/pull-request/`) shells out to `gh` through an injectable runner, which is how its tests avoid starting a process; the container picks `StubPullRequestGateway` under `AEOS_EXECUTOR=stub`, whose `needsPush` is false: stub mode neither pushes nor opens a pull request, and records the stub URL. `"pullRequests": { "enabled": false }` in `project.json` skips push and pull request. Never call the real `gh` or push from a test.

### Spec pin

`ticket create --spec <feature>` backs an epic with `features/<feature>/` of the artefact tree. `pinSpec` (`application/services/spec-pin.ts`, called by `TicketCreateUseCase`) checks, in order: the directory and its `spec.md`/`decisions.yaml` exist, the schema, the linter, no `ESCALATED` outcome, no uncommitted change under the feature; then pins `{ repo: '<key>-aeos', commit: <.aeos HEAD>, path: 'features/<feature>' }` (`domain/model/spec-pin.ts`). The schema and lint passes are one run of the seeded `lint_decisions.py` behind the `DecisionsLint` port (`infrastructure/spec/decisions-lint.adapter.ts`, injectable runner; it refuses to run without `python3`, `PyYAML` and `jsonschema`, because the linter would otherwise skip the schema pass silently). There is no JSON Schema validator among the runtime dependencies; `ajv` is a dev dependency for tests only. Only `spec_feature` and `spec_commit` are stored (migration v9). `TicketApproveUseCase` refuses to move an epic with no pin out of `BACKLOG` (one created before pins; the orchestrator's advance goes through the same use case), with the guidance of migration v10. **A task's pin is never copied**: always go through `resolveSpecPin` (`application/services/spec-pin.ts`), which falls back to the parent epic. It feeds `ticket show` (with the "spec has moved" warning from `GitGateway.pathChangedSince`), the `Spec:` commit trailer, the pull request body and `spec_pin` of every run record.

`TicketRunUseCase` passes the resolved pin to every `ContextAssembler.assemble` call. For a pinned ticket the assembler fills `AssembledContext.spec`/`specPin` from `spec.md`, `decisions.yaml`, each `features/*.feature` and the context's `glossary.md`, and appends the context's `CONSTRAINTS.md` after the project's. **It reads them only with `gitGateway.showFile`/`listFiles` at the pinned commit, never from the working tree, and never falls back**: an unreadable pin throws, and the run returns `failed` before anything executes. `buildContextSection` renders them as `## Specification (pinned <repo>@<short commit>)`, first in the context. With no pin the prompt is byte-identical to what it was; `prompt-builder.test.ts` holds that.

### Gate records

Every human decision is a `GateRecord` (`domain/model/gate-record.ts`, mirroring the human-owned `gates.schema.json`) appended by `GateRecorder` (`application/services/gate-recorder.ts`) through the `GateRecordStore` port. `FsGateRecordStore` appends as text (`records:` is the file's last key, so earlier records are never rewritten), numbers `GATE-<n>` per file and commits: `features/<feature>/gates.yaml` for a spec-backed ticket, `tickets/<id>/<id>-gates.yaml` otherwise. **The record is written before ticket state changes**; the recorder throws on a missing git identity (`GitGateway.userIdentity` of the project repository), a missing or short reason on an override or rejection, or a failed write, and the use case then leaves state alone. `approve`, `dod-approve`, `sign-off`, `move`, `answer` and `resolve` each call it; `approve` checks the identity first (`decidedBy`) and records last, after the pull request, so a failed pull request leaves no approval on record. The orchestrator passes `{ byEngine: true }` to approve, which records nothing: an auto advance is not a human decision. The `spec` gate is an approval out of a column whose role is `spec-review`. Because `gates.yaml` sits in the feature directory, `ticket show` excludes it from the "spec has moved" check, and the context assembler keeps `<id>-gates.yaml` out of prior artifacts.

### Amendments and repin

On a spec-backed ticket `TicketAnswerUseCase` hands the answered questions (`DecisionPromotionService.answered`) to `SpecAmendmentService` **before anything else is written**: it appends them to the feature's `decisions.yaml` through the `DecisionsFile` port (`YamlDecisionsFile` inserts text at the end of the `decisions:` list, so comments survive; ids are the next `NEW-<n>` and `AC-<n>` of the file), lints, and commits `decide(<feature>): amendment from <ticket>`; a lint failure restores the file with `restoreFiles`. The decisions schema needed no change: `question` and `evidence` carry the origin. The gate recorded is `amendment`, not `answer`, and the ticket stays `BLOCKED`. `pendingAmendment` (`services/spec-pin.ts`) finds an `amendment` gate record whose `spec_pin.commit` is still the current pin; it is the drift guard at the top of `TicketRunUseCase.execute` and the reason a second amendment is refused. `TicketRepinUseCase` (`ticket repin`) re-runs `pinSpec` (shared with `ticket create --spec`), records a `repin` gate under the old pin, then `setSpecCommit` on the epic and `READY` on a blocked ticket. The engine never edits `spec.md`.

### CLI contract

`cli-contract.yaml` (package root, shipped in `files`, protected by the built-in glob `**/cli-contract.yaml`) is the human-owned description of the command surface. **Never edit it**; when it and the code disagree, raise it. `src/cli/contract/`:

- `contract-schema.ts`: Zod schema of the file *after* `$ref` resolution, all `strictObject`, so an unknown key fails with its path. JSON Schemas (`data`, parameter `schema`) are opaque records.
- `load-contract.ts`: `parseContract` resolves every `{ $ref: "#/components/…" }` over the raw YAML first (a reference that points nowhere, has sibling keys or loops throws naming it), validates, then appends `globals.parameters` and merges `globals.responses` into every command. `loadContract()` reads the approved file.
- `lint-contract.ts`: `lintContract`, the hand-edit checks of the task (declared resources and exit codes, a `"0"` response with data, `"4"` when resources are required, a task on everything proposed, unique `operationId`s, argument positions, option/flag shape, the parameter-schema keyword subset).
- `verify-contract.ts`: `verifyContract(contract, program, envRead)` walks Commander's leaf commands and returns `{ mismatches, pending, landed }`. An item with `status: proposed` that is absent is `pending`; present, it is `landed` and must match. Text may be the current or the `pending` wording (then `landed`), never a third. `envVariablesRead(srcDir)` greps `process.env.AEOS_*` in non-test code (`*.test.*`, `*.smoke-test.*`, `*.fixture.*` and `e2e/` are test code). `requires` and the parameter-schema checks are generated from the contract. `responses` are held to it in tests: `contract-output.fixture.ts` has `schemaProblems` (every output schema compiles as JSON Schema 2020-12) and `outputProblems(contract, commandPath, stdout, exitCode)` (one envelope, an exit code the command declares, `data` valid for that code, `error.resource` exactly on 4), and `src/e2e/contract-output.e2e.test.ts` runs every built command under the stub with `--json` through it and fails when a command is not walked. It is a fixture because `ajv` is a dev dependency.
- `main.ts` is `npm run verify:contract` (via `tsx`); `verify-contract.test.ts` runs the same comparison in `npm test` and asserts there is no mismatch.

### Generated command registration

`scripts/generate-cli.mjs` (plain Node, run before the build; `npm run generate:cli`) reads the contract, resolves `$ref`s and applies the globals itself (`--resolved` prints that, and a test holds it equal to `loadContract()`), and writes `src/cli/generated/`: `commands.gen.ts` (`registerGenerated(program, handlers, resources, setExit)`, the whole Commander tree, the `Handlers` interface, and `run`), `types.gen.ts` (`<OperationId>Args`/`Options`/`Data`, and one type per name under `components.schemas`), `exit-codes.gen.ts` (`EXIT`, `ExitCode`, `CONTRACT_VERSION`), `resources.gen.ts` (`ResourceName`, `RESOURCES`, `COMMAND_RESOURCES`, `Declared<Id>`), `environment.gen.ts`, and the command reference between the `GENERATED CLI REFERENCE` markers of `README.md` and `skills/aeos/SKILL.md`. **Never edit any of it**: `src/cli/generated/**` is a built-in protected path, excluded from Prettier (`.prettierignore`), and `npm run verify:generated` (CI, and a test in `generate-cli.test.ts`) fails when a committed file differs.

- **What is generated.** Everything `existing`, with the current summary and description, never the `pending` one. Anything `proposed` is skipped (today only `dashboard`); a proposed resource has no guard and is left out of every `requires`. `verify:contract` lists a built item the contract still marks proposed as landed, and `verify-contract.test.ts` holds that list empty.
- **Handlers.** `src/cli/commands/<name>.handler.ts` exports `Handlers['<operationId>']`: `async (args, options, context) => CommandResult<Data>`. No Commander call and no resource check belongs there (a test greps for `.command(`/`.option(`); `commands/index.ts` collects them as `handlers`. `context` (`CommandContext` in `src/cli/resources.ts`) carries the `container`, `projectPath` (for a command that requires `project`), `prompt`, and `require(resource)`, typed to the resources that command declares, for a `conditionalRequires` case: it returns null, or the missing-resource result for the handler to return.
- **Results.** A handler never prints its result and never touches `process.exitCode` (assigned once, in `render.ts`; a test greps). It returns `done(data, text, warnings?)`, `stopped(situation, code, message, { data, text, stream, resource })` or `failed(error)` from `src/cli/result.ts`. `Data` is generated from the response schemas, so the wrong shape does not compile; the generator stops on a schema keyword that describes shape and that `tsType` does not know. `exitCodeFor` (`exit-code-mapping.ts`) is the only mapping to an exit code: a named situation, a ticket's sub-state, or a halt reason. `failed` gets its `error.code` from `classify` (`error-codes.ts`), which reads the use case's message (see the `shortcut` comment there: use cases still report errors as text); an escalated ticket run and a halted orchestrator run report the engine's `EscalationReason`/`HaltReason` as the code. `stream` exists because the exit code cannot say where text went before: an escalated run reported on stderr, an orchestrator halt on stdout.
- **`run`**, in the generated file, is the one path of every command: parameter checks compiled from each parameter's `schema` (`INVALID_ARGUMENT`, exit 2), then `requires` in order (exit 4, `error.resource`), then the handler, with anything thrown turned into `failed`; then `render` (`render.ts`) writes text (`text()` to its stream, each warning to stderr) or, under `--json`, exactly one envelope on stdout. What is thrown outside a command (Commander's usage errors, exit 2; the pipeline guard's refusal, exit 3 `PIPELINE_CHANGE_IN_FLIGHT`) is rendered by `runCli` in `index.ts`, which is why `buildProgram` calls `exitOverride()`. The Ink shell passes its own `setExit` to `buildProgram`, so a command run inside it never sets the process's exit code.
- **Prompts.** `src/cli/prompt.ts` (`Prompt`: `interactive`, `ask`) is the only way a command asks, and it asks on stderr. `ticket answer`/`ticket resolve` refuse with exit 2 when not interactive unless `--yes`, and a no at the terminal is exit 0 with `data` `{ ticketId, declined: true }` (nothing went wrong, nothing changed); `ticket dod-approve` refuses with exit 3 `CONFIRMATION_REQUIRED` before it reviews or records anything. A test passes its own `Prompt` as the third argument of `programWith`.
- **Under `--json`** `ticket run` and `orchestrator run` use `createJsonLinesDisplay` (`ui/ticket-run-display.ts`): no live view, each run event one JSON line on stderr. `ticket run` reads `ticketShow` before and after the run to report the run ids and cost the run added; a `null` among those costs makes `costUsd` null and adds the `COST_UNKNOWN` warning.
- **Guards.** `createResources(container)` in `src/cli/resources.ts` has one check per resource. `run` checks a command's `requires` in order inside the action, and the first one missing stops it with the contract's description and fix, exit 4, without calling the handler. Because guards run in the action, `install` and `project init` never touch `state.db`. The `executor` guard only checks a `--executor` override (see the `shortcut` comment there). `python` is `PythonDecisionsLint.ready()` (python3 imports `yaml` and `jsonschema`); `gh` is a file named `gh` on PATH, never run, and always in place under `AEOS_EXECUTOR=stub`. The conditional cases (`ticket create --spec`, an approval that opens a pull request) still reach exit 4 through `classify`, by the use case's wording.
- **Group descriptions** (`project`, `ticket`, `orchestrator`) are not in the contract; `buildProgram` sets them (`GROUPS` in `src/cli/index.ts`).
- **Tests.** `commands/program.fixture.ts` (`programWith(container)`) registers the generated tree with the real handlers over a mocked container; only the `project` guard is real there, since the others would open this machine's database. Handler tests parse real argv through it, with `parseAsync`: `run` is asynchronous, so nothing is written before it is awaited. `src/cli/json-output.test.ts` holds the output and exit-code behaviour of the commands; the end-to-end harness's `runCli` goes through the real `runCli` and returns `stdout` apart from the rest.

### Column roles

**No code compares a column against a name** other than the structural `BACKLOG` and `DONE`; `src/column-names.test.ts` fails the build if one does. What a column is for is declared in its spec: `role` (`COLUMN_ROLES` in `domain/model/column-spec.ts`: `standard`, `spec-review`, `decomposition`, `integration`, `final-gate`; the approved vocabulary of `templates/pipelines.yaml`, which a test holds the constant to), `diffContext` (`none`/`task`/`epic`) and `executorMode` (absent means `artifact`; nothing is agentic by name). All three are optional on `ColumnSpec` and defaulted by the Zod schema, so a hand-built spec in a test with no role is `standard`.

- `domain/` gets roles as data: `OrchestratorPolicyInput.roleOf`, next to `autoAdvance`. `decomposition` + `SIGNED_OFF` is "drive the children"; `final-gate` is run once (spec-backed epics only), then the `HUMAN_GATE` halt; it is never advanced.
- `application/services/column-roles.ts` is where use cases ask: `columnSpecOf` (null for `BACKLOG`/`DONE`), `roleOf` (**throws when a spec cannot be loaded**, because a final gate mistaken for a standard column would be advanced past) and `findColumnSpec` (first of the columns given, a kind's pipeline, whose spec matches; how a task's pull request finds the review of the `diffContext: task` column). `TicketRunUseCase` already holds the column's spec and reads it directly.
- `ContextAssembler.assemble` takes the `diffContext`, not the column.
- `YamlColumnSpecLoader` reads every `*.yaml` of `.aeos/column-specs/` and indexes it by its own `column:` field (`specFiles`); file names mean nothing, and two files declaring one column throw naming both, for `load` and for `labels`.

### Pipelines

Column order is data: `.aeos/pipelines.yaml`, scaffolded from the human-owned, approved `templates/pipelines.yaml` (never edit it). `Column` is a `string`; only `Column.BACKLOG` and `Column.DONE` are constants, so tests write other columns as literals (`'CODE_REVIEW'`). `domain/model/column.ts` holds `Pipelines` (`Record<TicketKind, Column[]>`) and the pure `columnOrderFor`/`nextColumnFor`/`isColumnInPipeline`/`isValidColumn`, which all take the loaded pipelines first, plus `displayOrder` (every column once, for labels and listings).

- `PipelineLoader` port → `YamlPipelineLoader` (`infrastructure/spec-loader/`). `load(root)` reads the file (a project without one gets `templatePipelines()`), then applies `pipelineErrors` (`domain/services/pipeline-validation.ts`): the rules in the header of the approved file, plus the two the I1-M4-005b task file adds (an `EPIC` pipeline has exactly one `spec-review` column, before the `decomposition` column, which is question 3 of that file, accepted at sign-off; a `TASK` pipeline has no `spec-review`, `decomposition` or `final-gate` column). The header's rule that an `EPIC` pipeline has **exactly** one `final-gate` column (owner, 11 Nov 2026; it said "at most one" before) has a message for none that points at `aeos project sync`. Roles come from the column specs, which is why the loader takes a `ColumnSpecLoader`. A key other than `EPIC`/`TASK` is refused before the Zod schema (`PipelinesSchema`) runs, for a message that says kinds cannot be added.
- `readPipelines(root)` is the same file without the role rules. `YamlColumnSpecLoader.labels` uses it for the list of columns: the validating loader loads column specs, so labels cannot go through it.
- Readers: `TicketApproveUseCase` (next column; the task pipeline for `findColumnSpec`), `TicketMoveUseCase` (the target must be in the ticket's own pipeline; the CLI hands an unknown status on as typed so the use case can list that pipeline), `OrchestratorUseCase.assertExecutorsReportCost`. In a test, `{ load: () => templatePipelines() }` is a pipeline loader.
- A ticket's column is not checked against the pipelines when read from the database; the order-change guard is what keeps a ticket from being stranded.

**Order-change guard.** `PipelineGuard` (`application/services/pipeline-guard.ts`) compares each kind's loaded pipeline with the one last accepted (`pipeline_state`, migration v13, `PipelineStateRepository`). First sight stores it; an unchanged one is a no-op; a changed one is accepted (gate record first via `GateRecorder.recordPipelineChange`, then stored, then one line through `notify`) unless a ticket of that kind `isInFlight` (`domain/services/pipeline-change.ts`: neither `BACKLOG` nor `DONE`), in which case `check` throws naming the tickets and the previous order. It is hooked **once**, in `buildProgram`'s Commander `preAction` hook, for every `ticket`/`orchestrator` command except the read-only ones (`ticket list`, `ticket show`, `orchestrator status`); the Ink shell's direct `ticket run` path calls `container.checkPipelines` itself. The refusal is thrown out of `parseAsync`; `runCli` renders it like any result, with exit code 3 and `error.code` `PIPELINE_CHANGE_IN_FLIGHT`. Read-only commands get their labels from `guard.accepted()` (`container.columnLabels`), so a column the file dropped still has one. The `pipeline-change` record has no ticket: `ticket: 'pipelines'` puts every such record in `.aeos/tickets/pipelines/pipelines-gates.yaml`, and the old and new order are its `reason`, the only free text the approved schema has.

### Column labels

A column's identifier is fixed and is the only thing persisted; the name shown is a label (`label` in the column spec, `labels` in `project.json` for `BACKLOG`/`DONE`, default sentence case). Everything about labels is in the pure `domain/services/column-labels.ts`: `labelFor`, `resolveColumn` (identifier or label in, identifier out; the identifier wins), `labelErrors`, and `withColumnLabels`, which substitutes labels into text built with identifiers. That last one exists because halt messages and use-case errors are built (and halt messages stored) with identifiers: **labels are applied in `cli/` at print time and never passed into `application/` or `domain/` output**. `YamlColumnSpecLoader.labels(root)` builds and validates the map and `load()` calls it, so invalid labels fail every load. Commands get it as a `getLabels(projectPath)` resolver from the container (`columnLabels`; `columnLabelsOfProject` for the cross-project `aeos costs`), not by importing the loader. The Ink shell's run pane (`ticket-run-shell-state.ts`) still shows the identifier.

### Loop termination

"Iterate until the reviewer approves" does not terminate on its own. Four guards in `domain/services/review-loop-policy.ts` make it finite: severity gate (only `REJECTED` blocks), iteration cap (`reviewLoop.maxIterations`, default 5, column spec overrides global), convergence detection (a retry reproducing the previous blocker topics escalates early), and the orchestrator's budget ceiling. Keep this function pure — it is the most heavily tested logic in the repo.

### Orchestrator

`src/application/orchestrator.use-case.ts` drives an epic and its tasks. **The scheduler is a pure function, not an LLM** (`domain/services/orchestrator-policy.ts` → `decideNextAction`): ask what to do, do exactly that one thing, ask again. Putting a model in the control path would make "why did this advance?" unanswerable from the transition log. Every loop exit is a named `HaltReason`, including the successful ones. Per-epic status, pause state, and budget live in `orchestrator_state` (migration v3).

**Unknown cost is `null`, never `0`.** `cost_records.cost_known` (migration v6) carries it; rows from before that migration read back as unknown. `reportsCost` in `domain/services/executor-capabilities.ts` says which executors report (`claude-cli`, `stub`). A budget is refused up front if any agent of a column still ahead resolves to one that does not (the epic's current and later columns; each task column unless the epic is past `TASK_BREAKDOWN` and every child is past it), and the policy halts with `COST_UNKNOWN` if a budgeted epic still ends up with a `null` cost record; `aeos orchestrator clear-budget <epicId>` (`OrchestratorPort.clearBudget`) sets the persisted budget to `null`, which is the only way out, since the `null` record stays. A failed executor run also records `null`. Each cost record carries its `role` (`preflight`/`worker`/`reviewer`, migration v7; absent on older rows); `aeos costs` (`costs.use-case.ts`) aggregates across all projects from the global DB and never folds an unknown cost into a total.

### Specs, rubrics, and agents are data, not code

Column behaviour lives in YAML under a project's `.aeos/`:

- `.aeos/column-specs/*.yaml` — which worker/reviewer agent a column uses, execution mode, validation rules
- `.aeos/agents/*.yaml` — agent prompts and default executor/model
- `.aeos/rubrics/` — reviewer rubrics
- `.aeos/CONSTRAINTS.md` — project-specific architecture/style/security rules injected into agent context

Changing pipeline behaviour usually means editing YAML, not TypeScript. Loaders validate with Zod (`infrastructure/spec-loader/`).

`templates/` at the package root holds the starter copies of `column-specs/`, `agents/`, and `rubrics/` that `aeos project init` scaffolds into a new project (`infrastructure/filesystem/template-source.ts`). They are plain YAML/Markdown rather than embedded strings, and ship via the `files` field in `package.json`. **Adding a column means adding its template spec too** — otherwise a fresh project fails on its first `ticket run` when a ticket reaches that column. `template-source.test.ts` guards this by scaffolding a temp project and asserting every column spec loads and its agents and rubrics resolve. Removing a template means adding its path to `RETIRED_TEMPLATES` in `project-sync.use-case.ts`, so `aeos project sync` reports a project's leftover copy as `obsolete` (reported, never deleted).

`.aeos/` is also the project's **artefact tree** (decision D1): `features/<feature>/` holds a human-written spec, `contexts/<context>/` a glossary and constraints, `schemas/` the artefact schemas. `ArtefactTree` (`domain/ports/driven/artefact-tree.port.ts`) resolves its root: `artefactTree` in `project.json`, default `.aeos`. The schemas have one authored copy, `plugins/artefact-tree-pipeline/schemas/`. `templates/schemas/` is a generated copy made by `npm run build` (it runs the plugin's `seed-schemas.mjs`, which also writes the `.source` stamp); `npm run lint` fails when it is stale. Because it sits under `templates/`, `project init` seeds it and `project sync` reports drift like any other template. Never edit `templates/schemas/` by hand. The spec skills live in the same plugin; `aeos-core/skills/aeos/` is a different thing.

`skills/aeos/SKILL.md` (also shipped via `files`) teaches an agentic executor to drive the `aeos` CLI. `project init` copies it to `.aeos/skills/aeos/` and relative-symlinks it into each executor's skills dir (`.claude/skills`, `.augment/skills` — see `skill-source.ts`). The **portable** carrier of the decomposition instruction is the architect's `taskInstruction` (in the prompt, so every executor gets it); the skill is reinforcement for skill-aware backends. This is how `TASK_BREAKDOWN` decomposition works: that column is **agentic**, and the architect calls `aeos ticket create --parent <epic> --key T-NNN` to create the child tasks itself rather than AEOS parsing them out of an artifact. `requiresRepoDiff: false` on that column stops the agentic diff check (which enforces the IMPLEMENTATION guarantee) from failing a run that creates tickets rather than editing the repo.

`ticket create` is idempotent under a parent: it keys on `--key` (the task's stable `T-NNN` label) when given, else the title (and, as a bridge, a keyless prior child with a matching title). The key matters because a review-loop retry re-runs the _agent_, which may rephrase a task's title — title-only dedup would then duplicate it; the key survives the rephrase (`task_key`, migration v4). A key match leaves the existing task **unchanged** (a reworded title is not applied), and each task must have a **distinct** key — a reused key collapses two tasks into one. Both constraints are stated in the architect prompt and skill. The orchestrator needs no special decomposition step: children created during the run are picked up by its existing "drive all children" logic on the next tick; `AWAITING_DECOMPOSITION` remains only as the fallback when none appear (e.g. under `AEOS_EXECUTOR=stub`, which can't shell out). Tickets are created mid-run, before the breakdown is reviewed — the key keeps retries from accumulating, but a breakdown that is _abandoned_ after removing a task leaves an orphan child in `BACKLOG`; the epic's DONE-join lists it, and the operator clears it with `aeos ticket move <id> DONE --reason "…"`. Auto-deleting is deliberately avoided.

### State

- **SQLite at `~/.aeos/state.db`** — the source of truth for tickets, transitions, and costs. All projects share one DB, isolated by `project_id`. Path overridable via `AEOS_HOME`.
- **`<project>/.aeos/tickets/<ticketId>/`** — artifacts, named `<ticketId>-<artifact>.md`. Ticket state is mirrored into a markdown file on disk via `syncTicketDocument`, but **git carries artifacts only** — no commit on sub-state transitions. SQLite is authoritative for state; committing every transition buried the artifact history a human actually reads. Don't reintroduce `[STATE]` commits.
- **`<project>/.aeos/tickets/<ticketId>/runs/`** — one run record per executor invocation or checks stage (`<run_id>.json`, `.brief.md`, `.log`; a checks record has no brief), written by `writeRunRecord` in `TicketRunUseCase` through `RunRecordStore`, on success and failure alike. `domain/model/run-record.ts` mirrors the human-owned `run-record.schema.json` field for field; the end-to-end test validates every record against it. A record is committed with the artifact it produced (which ends with an `AEOS-RUN` link to it), or alone when there is none. Preflight is recorded by wrapping the executor handed to `PreflightService`.
- `Ticket` carries `kind` (`EPIC`/`TASK`) and `parentId`. Migration v2 backfills existing rows as epics and folds retired `ARCH_SPIKE` tickets into `TECH_SPEC`. Migration v10 renames `PRODUCT_SCOPING` to `SPEC_REVIEW` in `tickets`, `transitions` and `cost_records`, and sets an epic it finds there with no pin `ESCALATED` (`SPEC_REQUIRED`). Migrations must be idempotent — `ALTER TABLE ADD COLUMN` is not, so guard with `hasColumn`.

### Executors

`Executor` (`domain/ports/driven/executor.port.ts`) is a two-method port: `run(invocation)` and `interrupt()`. Adapters in `infrastructure/executor/` spawn external CLIs. Resolution order for a run is override flags → `.aeos/project.json` → agent spec → built-in default (see `ExecutorConfigResolver`).

Only `claude-cli`, `auggie-cli`, `opencode-cli`, and `stub` support agentic `IMPLEMENTATION`; `ollama-cli` is artifact-only and is rejected for those runs. Agentic implementation runs must leave a real git diff or validation fails.

Set `AEOS_EXECUTOR=stub` to exercise the pipeline without real LLM calls. The container reads the variable and passes it to `ExecutorConfigResolver`, which then resolves every agent to `stub`, so run records, cost records and the budget refusal all see `stub`. The stub is role-aware by output path: it answers `NO_BLOCKERS` for preflight, emits an `AEOS-VERDICT` trailer for reviews (a worker artifact named `<id>-{spec,code,integration}-review.md` is not one), answers `pass` in an `AEOS-CONFORMANCE` block for every criterion a prompt tells it to judge, and pads its artifact past `minWordCount`. If you change the verdict contract or raise a word count, update the stub too — otherwise `AEOS_EXECUTOR=stub` stops working. Unit tests mock the executor and will not notice; `src/e2e/pipeline.e2e.test.ts` will. It drives an epic, its tasks and a standalone task to `DONE` through the real CLI with the stub, in a temp `AEOS_HOME` and project, and runs in `npm test`. Build new end-to-end cases on `src/e2e/harness.ts`. Outside the bug track the stub writes no repository change, so the harness wraps it to add one on `IMPLEMENTATION` runs; without that wrapper a stub `IMPLEMENTATION` run fails the git-diff guarantee.

## Conventions

- ESM throughout (`"type": "module"`, `module: NodeNext`). **Relative imports must carry the `.js` extension**, including from `.ts` sources.
- Each layer has a barrel `index.ts`; import across layers through those.
- Tests are colocated (`*.test.ts` next to the source). `*.smoke-test.ts` files are excluded from the Vitest `include` glob and run via tsx.
- TUI components are `.tsx` and tested with `ink-testing-library`.
- ESLint: `@typescript-eslint/no-explicit-any` is an **error**; `no-console` warns (CLI output goes through `render.ts`, Ink or explicit writers, not stray `console.log`).
- TypeScript is `strict`.
