# Tooling: Generating jOOQ (Kotlin/Spring) from SQL migrations

Enforcement tooling for **Principle IV — Generators build the scaffold, agents write the logic**, for
the **database layer** of a Kotlin + Spring Boot service. A human owns the Flyway migrations; this
generates the jOOQ classes the agent is not allowed to hand-write (the typed table/record DSL), from
the *real migrated schema*, and fails the build the moment a column has a SQL type the project has
not accounted for.

It is modelled on how a production Kotlin/Spring service does DB codegen — Flyway SQL migrations and
jOOQ generated from a dockerized Postgres — behind the same editable-policy + reusable-verifier split
as the OpenAPI scaffolds in this folder. It is the DB sibling of
[`../sqlmigrations-typescript`](../sqlmigrations-typescript).

## What it produces

From `src/main/resources/db/migration/V*.sql`, via Flyway → Postgres → jOOQ:

- `build/generated-jooq/<basePackage>/tables/*.java` — one typed `Table` per table (and a `Record`
  per table), plus `Keys`, `Indexes`, the schema/catalog classes. You use them through the jOOQ DSL;
  you never hand-edit them.

A committed **reference copy** lives in [`examples/generated/`](examples/generated) so you can read
the shape without running anything. `build/` itself is gitignored.

## Why it is more than running the jOOQ plugin

Three disciplines, all in the reusable verifier ([`scripts/verify-schema.gradle`](scripts/verify-schema.gradle)) —
you do not edit it:

1. **The emitter is pinned.** jOOQ stamps its version into every generated file's `@Generated`
   annotation; the verifier reads it and refuses to pass unless it equals `pinnedJooqVersion` in the
   policy. The plugin selects a default jOOQ version per release, so a plugin bump that changes the
   generator cannot silently retype the schema without re-verifying and moving the pin.
2. **No silent no-op.** At least one generated table class must exist and be non-empty. A green build
   with no generated schema surfaces much later as a wall of unresolved references.
3. **An unmapped type breaks the build.** Every generated field's Java type is checked against the
   policy's allow-list. The headline refusal is **`Object`** — jOOQ's fallback for a SQL type it could
   not map (a custom type, a composite, an unconfigured extension type, an enum without a forced
   type) — the database equivalent of an unmodelled OpenAPI construct. Value-level `checks` then run
   over the parsed tables (here: every table carries a `CREATED_AT`/`UPDATED_AT`).

## Run it

```bash
./gradlew generateDb      # generateJooqClasses + verifySchema
```

Expected tail:

```
verifySchema: build/generated-jooq is current - 4 tables, 23 fields, emitter jOOQ 3.21.2.
BUILD SUCCESSFUL
```

Requires **Docker running** (Docker Desktop, colima, …) and a JDK the pinned Gradle supports. If
`docker` works but generation cannot find the daemon, point Testcontainers at your socket, e.g. for
colima:

```bash
export DOCKER_HOST="unix://$HOME/.colima/default/docker.sock"
# optional: export TESTCONTAINERS_RYUK_DISABLED=true
```

## Install (into a real Kotlin/Spring project)

Copy into your project:

```
jooq-policy.gradle
scripts/verify-schema.gradle
```

Merge [`build.gradle.snippet`](build.gradle.snippet) into your `build.gradle` (the plugin, the two
`apply from`, the generate task, the `compileKotlin` gate), put your migrations in
`src/main/resources/db/migration`, point `basePackageName`/`out` in `jooq-policy.gradle` at your
package, then `./gradlew generateDb`. The gate makes `build` regenerate + verify first, so nothing
compiles against a stale or unverified schema — a CI job that runs `build` (which needs Docker)
enforces the whole thing.

## Extending it — the policy file

[`jooq-policy.gradle`](jooq-policy.gradle) is the only file you edit:

| Key | What it controls |
|---|---|
| `out`, `basePackageName` | Where the generated jOOQ goes and its package. |
| `pinnedJooqVersion` | The jOOQ version this policy is verified against. |
| `allow.fieldTypes` | Generated field Java types the schema may contain. A type not here is refused or breaks the build. |
| `refuse` | Java types you have decided not to carry untyped (keyed by type, value is the reason). |
| `checks` | Value-level closures over the parsed tables that throw to fail the build. |

When you decide to serve something currently refused, the move is always: map it (a jOOQ `forcedType`
binding, or a schema change), then move the type to `allow.fieldTypes` in the same change.

## Notes

- Reference generated by the pinned **jOOQ 3.21.2** against a real migrated `postgres:16-alpine`, via
  the **`dev.monosoul.jooq-docker` 8.0.21** plugin — the maintained successor to the (abandoned)
  `com.revolut.jooq-docker` 0.3.9 a production service may still use; the successor runs on modern
  Gradle/JDK. The pin is the one knob you re-verify on a bump.
- The committed reference is a **representative snapshot**, not byte-reproducible: jOOQ embeds a
  per-run `configuration hash` in each `@Generated` annotation (it hashes the codegen config, which
  includes the throwaway container's port), so that one line changes between runs. The verifier's gate
  is the pin/no-op/type checks, not output parity, and the `jOOQ version:` stamp it pins against is
  stable.
- jOOQ infers types from the SQL schema, not from `CHECK (… IN (…))` constraints, so the example's
  `status`/`entry_type` land as `String`. For a typed enum, use a Postgres `ENUM` plus a jOOQ
  `forcedType`, and add its generated type to `allow.fieldTypes`.
- Verified end to end on Docker (colima): happy path plus all three guards (an `Object` field, a
  version-pin mismatch, and the missing-timestamp convention).
